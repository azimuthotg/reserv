# หนังสือตอบกลับ — เพิ่มกติกาห้ามจองทับเวลาเรียบร้อยแล้ว

**ถึง:** ทีมพัฒนา LRS ARC VM Gateway
**จาก:** ผู้ดูแลระบบจองพื้นที่บริการ (reserv) สำนักวิทยบริการ มหาวิทยาลัยนครพนม
**วันที่:** 8 ส.ค. 2569
**อ้างถึง:** ใบแจ้งขอเพิ่มกติกาการจอง — ห้ามผู้ใช้รายเดียวจองทับเวลากันข้ามห้อง ลงวันที่ 8 ส.ค. 2569
**เรื่อง:** ตอบกลับ — ดำเนินการครบทั้ง 5 ข้อ

---

## 1. สรุปสิ่งที่ดำเนินการ

| ข้อ | คำขอ | ผล |
|---|---|---|
| 1 | ตรวจเวลาทับซ้อนของผู้ใช้รายเดียวกัน ข้ามทุกห้อง ในวันเดียวกัน | ✅ **เพิ่มแล้ว** |
| 2 | ยกเว้น `meeting_f1` ทั้งสองทาง | ✅ **ยกเว้นแล้ว** (ทั้งขาใหม่และขาเดิม) |
| 3 | ใช้เงื่อนไข "ทับจริง" (`<`) ให้จองต่อกันพอดีได้ | ✅ **ใช้ `<` ตามที่ระบุ** |
| 4 | แจ้งผู้ใช้ว่าชนกับการจองรายการใด | ✅ **บอกชื่อห้อง + ช่วงเวลา** |
| 5 | แจ้งกลับเมื่อเสร็จ | ✅ หนังสือฉบับนี้ |

ทั้งหมดตรวจที่ `create_booking()` ซึ่งเป็น **จุดสร้าง booking จุดเดียวของระบบ** และระบบไม่มีหน้าแก้ไข
การจอง (มีเฉพาะยกเลิก) จึงไม่ต้องใช้เงื่อนไข `editing_id` ตามที่ใบแจ้งเผื่อไว้

## 2. ผลทดสอบเทียบกับตารางพฤติกรรมที่ขอมา

ทดสอบอัตโนมัติครบทุกแถวแล้ว (ชุดทดสอบทั้งระบบ **23/23 ผ่าน** เพิ่มใหม่ 6 กรณี)

| กรณี | ที่ขอ | ผลจริง |
|---|---|---|
| คนละช่วงเวลา ต่างห้อง | ✅ จองได้ | ✅ ตรง |
| ทับเต็ม ต่างห้อง | ❌ ปฏิเสธ | ✅ ตรง (HTTP 409) |
| ทับบางส่วน | ❌ ปฏิเสธ | ✅ ตรง |
| ต่อกันพอดี 10:00–11:00 + 11:00–12:00 | ✅ จองได้ | ✅ ตรง |
| `meeting_f1` + ห้องอื่น ทับกัน | ✅ จองได้ | ✅ ตรง **ทั้งสองทาง** |
| `meeting_f1` ซ้ำวันเดียวกัน | ตามกติกาเดิม 1 ครั้ง/วัน | ✅ ตรง |
| การจองที่ยกเลิกแล้ว | ไม่ควรบล็อก | ✅ ไม่นับ |
| ผู้ใช้คนอื่นจองเวลาเดียวกัน | ต้องไม่กระทบ | ✅ ไม่กระทบ |

**ข้อความที่ผู้ใช้จะเห็น**

> คุณมีการจอง **MINI THEATER** เวลา **13:30–17:00** อยู่แล้วในวันเดียวกัน
> ไม่สามารถจองซ้อนช่วงเวลาเดียวกันได้ กรุณาเลือกช่วงเวลาอื่น

## 3. จุดที่ทำต่างจากใบแจ้ง (ผลลัพธ์เหมือนกันทุกประการ)

ใบแจ้งเสนอ SQL ที่ฝังชื่อห้องไว้ตรง ๆ (`r.booking_name <> 'meeting_f1'`)
สำนักฯ เลือก **เพิ่มฟิลด์ `Room.allow_overlap` (Boolean)** แล้วยกเว้นจากค่าในฟิลด์แทน

**เหตุผล:** ปัจจุบัน**ไม่มีชื่อห้องถูก hardcode อยู่ในโปรแกรมเลยแม้แต่จุดเดียว** ทุกอย่างอ่านจากฐานข้อมูล
หากฝังชื่อ `meeting_f1` ลงไปจะกลายเป็นจุดแรก และทุกครั้งที่นโยบายเปลี่ยนจะต้องแก้โปรแกรม + deploy ใหม่
ส่วนวิธีนี้เจ้าหน้าที่ติ๊กเองได้ที่หน้า `/manage/rooms/`

**สถานะปัจจุบัน: ติ๊กยกเว้นเฉพาะ `meeting_f1` ห้องเดียว** = พฤติกรรมตรงกับที่ขอมา 100%

| `booking_name` | `allow_overlap` |
|---|---|
| `mini`, `edutainment`, `canva`, `canva2`, `netflix1_vm` | `False` (กันทับเวลา) |
| `meeting_f1` | **`True`** (ยกเว้น) |

**อีก 2 จุดที่ปรับจากตัวอย่าง SQL:**

1. ตรวจ**ภายใน transaction เดียวกับการตรวจห้องชน** พร้อมล็อกแถว (`SELECT ... FOR UPDATE`)
   ไม่ใช่ `SELECT COUNT(*)` แยก — ถ้าใช้ count ลอย ๆ คำขอสองรายการที่เข้ามาพร้อมกันจะลอดผ่านได้ทั้งคู่
2. คัดห้องที่ยกเว้นด้วยรายการ id แทนการ join ตาราง `booking_room` เพื่อไม่ให้การล็อกแถวลามไปล็อกข้อมูลห้อง

## 4. ขอแก้ข้อมูลในใบแจ้ง 1 จุด (เพื่อไม่ให้อ้างอิงต่อผิด)

ใบแจ้งระบุว่า *"รหัส 11 หลักคือนักศึกษาจริง ไม่ใช่บัญชีทดสอบ"* — สำนักฯ ตรวจสอบแล้วพบว่า
**6 ใน 11 คู่เป็นบัญชีเดียวกันคือ `3489900017383` ซึ่งเป็น "บุคลากร"** (13 หลัก = เลขบัตรประชาชน
ไม่ใช่รหัสนักศึกษา) และเกิดขึ้นระหว่าง **20 เม.ย. – 8 พ.ค. 2569** ซึ่งเป็นช่วงเปิดระบบใหม่
เกือบทั้งหมดเป็นการทดสอบของเจ้าหน้าที่

เมื่อหักบัญชีดังกล่าวและหักคู่ที่มี `meeting_f1` (ซึ่งได้รับการยกเว้น) แล้ว
**เคสของนักศึกษาจริงที่กติกาใหม่จะป้องกันได้มี 4 คู่**

**แต่สำนักฯ เห็นด้วยกับข้อเสนออยู่ดี** เพราะน้ำหนักไม่ได้อยู่ที่จำนวน แต่อยู่ที่ว่าห้องไหนถูกล็อกทิ้ง:

| วันที่ | ทับกัน | ผลเสีย |
|---|---|---|
| 11 ก.ค. 69 | `mini` + `netflix1_vm` 13:30–17:00 | Netflix ถูกล็อกทิ้ง 3 ชม. 30 นาที |
| 17 ก.ค. 69 | `edutainment` + `netflix1_vm` 13:30–14:50 | Netflix ถูกล็อกทิ้ง 1 ชม. 20 นาที |

**`netflix1_vm` มีการจองทั้งหมดเพียง 20 รายการ — 2 รายการในนั้นคือผู้จองที่ไปอยู่ห้องอื่น คิดเป็น 10%**
และเคสล่าสุด (6 ส.ค. 69) เพิ่งเกิดเมื่อ 2 วันก่อน ยืนยันว่าเป็นปัญหาที่ยังดำเนินอยู่จริง

## 5. ข้อมูลย้อนหลัง — ยืนยันตรงกับที่ทีมพัฒนาแจ้ง

สำนักฯ ตรวจซ้ำด้วยเงื่อนไขเดียวกันบนข้อมูลทั้งตาราง (303 การจองสถานะ confirmed) ได้ผลตรงกัน:

- คู่ที่ทับเวลากัน **11 คู่** เท่ากันพอดี
- **ไม่มีคู่ใดมีวันจองตั้งแต่ 8 ส.ค. 2569 เป็นต้นไป** → ไม่ต้องยกเลิกหรือติดต่อนักศึกษารายใด
- **ทับกันในห้องเดียวกัน 0 คู่** → ยืนยันว่าการตรวจห้องชนแบบเดิมทำงานถูกต้องมาตลอด ปัญหาเป็นเรื่องข้ามห้องล้วน ๆ

## 6. ข้อจำกัดที่ควรทราบ

**เจ้าหน้าที่ยังสร้างการจองผ่านหน้า Django Admin ได้โดยข้ามกติกานี้** ถือเป็นช่องทาง override
สำหรับกรณีจำเป็น ส่วนช่องทางที่นักศึกษาใช้ (LINE OA / เว็บ) ถูกกันครบทุกกรณี

**แผนบริการนอกเวลาในอนาคต:** สำนักฯ กำลังพิจารณาเปิดรอบกลางคืนโดยให้สิทธิ์แยกจากรอบกลางวัน
กติกาที่เพิ่มรอบนี้**ไม่ขัดกับแผนดังกล่าว** เพราะรอบกลางวันกับกลางคืนเป็นช่วงเวลาที่ไม่ทับกันโดยนิยาม
การจองคนละรอบจึงไม่มีทางถูกกติกานี้บล็อก

---

## 7. การมีผลบังคับใช้

การแก้ไขครั้งนี้**มีการเปลี่ยนโครงสร้างฐานข้อมูล** (เพิ่มคอลัมน์ `allow_overlap` ในตาราง `booking_room`)
คอลัมน์ถูกเพิ่มลงฐานข้อมูลแล้ว และจะมีผลกับการจองจริงเมื่อระบบบนเซิร์ฟเวอร์โหลดโปรแกรมชุดใหม่
สำนักฯ จะแจ้งยืนยันอีกครั้งเมื่อดำเนินการเสร็จ เพื่อให้ทีมพัฒนาตรวจสอบข้อมูลยืนยันตามที่แจ้งไว้ในข้อ 5
