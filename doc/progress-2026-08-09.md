## 4.1 ขยายขนาด QR code ทุกช่องทาง (งานค้างจาก inbox 23 ก.ค.)

เดิม 5 หน้า hardcode ขนาดคนละค่า → รวมมาไว้ที่ helper กลาง
[booking/static/booking/js/qr.js](../booking/static/booking/js/qr.js) — `NPUQr.render(el, text, {reserve, max})`

| หน้า | เดิม | ใหม่ (จอ 375px) | ใหม่ (จอ 320px) |
|---|---|---|---|
| `/card/` · `/card-login/` | 180 | **279** (+55%) | 224 |
| `/external/` · `/external/permanent/` | 200 | **271** | 216 |
| `/manage/external/<id>/` (staff) | 160 | **240** | 200 |

- ขนาดคิดจาก `window.innerWidth` ลบ padding ของแต่ละหน้า (`reserve`) แล้ว clamp ที่ 200–320 px
- วาดที่ **ความละเอียด 2 เท่า** แล้วย่อด้วย CSS → ขอบโมดูลคมบนจอ retina
- เพิ่ม/ลดขนาดทั้งระบบภายหลังให้แก้ `MIN_PX`/`MAX_PX` ในไฟล์เดียว

### กับดักที่เจอระหว่างทาง (บันทึกใน MEM.md)

qrcodejs วาดลง `<canvas>` แล้วสลับเป็น `<img>` — **แต่บน UA ที่เป็น Android มันไม่สลับ** (คง canvas ไว้
และปล่อย `<img>` ว่างซ่อนไว้ เพราะ `_getAndroid` อ่าน "Android 14" ไม่ออก) ถ้าตั้งขนาดด้วย JS รายโหนด
จะพลาดโหนดที่เกิดทีหลัง → เปลี่ยนไปคุมด้วย CSS ที่ตัวครอบ (`[data-npu-qr]>canvas,>img{width:100%}`)
ซึ่งครอบคลุมทั้ง 2 เส้นทาง · **ห้ามแตะ `display`** ไม่งั้น canvas ที่ถูกซ่อนจะโผล่ซ้อนกับ img

### ตรวจแล้วบนเบราว์เซอร์จริง

| viewport | ผล |
|---|---|
| 320 × 720 | 224 / 216 / 200 px · ไม่ล้นแนวนอน |
| 375 × 812 (UA Android) | 279 / 271 / 240 px · แสดงผ่าน **canvas** (เส้นทาง Android) ถูกต้อง |
| 1280 (desktop) | 320 / 320 / 240 px (ชนเพดาน) · แสดงผ่าน **img** · ไม่ล้น |

template ทั้ง 5 ไฟล์ compile + render ผ่าน และมี `qr.js` + `NPUQr.render` ครบทุกไฟล์

### Deploy production (ทำแล้ว ✅)

`git pull` → `.\venv\Scripts\python.exe manage.py collectstatic --noinput` → **1 static file copied** (`qr.js`)
ผู้ใช้ restart service ไปด้วย (ไม่จำเป็นแต่ไม่เสียหาย)

**ผลตรวจบน production:**

| ตรวจ | ผล |
|---|---|
| `/reserv/static/booking/js/qr.js` | ✅ 200 · `text/javascript` · 2,877 bytes · มี `NPUQr`, `MIN_PX = 200`, `MAX_PX = 320` |
| `/reserv/card-login/` โหลด script | ✅ มี `<script src="/reserv/static/booking/js/qr.js">` (prefix `/reserv/` ถูกต้อง) |
| วาด QR จริงบนหน้า production (จอ 375) | ✅ 279 px · canvas internal 558 · ไม่ล้นแนวนอน |
| วาด QR จริงบนหน้า production (desktop) | ✅ 320 px · canvas internal 640 |
| console error | ✅ ไม่มี |

> ทดสอบแบบ **อ่านอย่างเดียว** — เรียก `NPUQr.render()` ลง element ชั่วคราวแล้วลบทิ้ง ไม่ล็อกอิน ไม่ส่งฟอร์ม
> ไม่มีการออกรหัส QR จริงให้ใครระหว่างทดสอบ

## 4.2 รูปห้อง 3 บริการ VM + แก้กล่องรูปให้เป็น 16:9

ผู้ใช้ generate รูปด้วย AI มา 3 ใบ (2752×1536) **มีชื่อบริการพาดอยู่ส่วนบนของภาพ**
ตกลงกันว่า **ไม่ใส่คำว่า Online ในรูป** เพราะการ์ดบอกไปแล้ว 2 จุด (📍 location + 🕐 เวลา)
และหน้ารายละเอียดมี chip `💻 บริการออนไลน์ ไม่ต้องเข้าอาคาร` อีกจุด — ชื่อในรูปมีไว้เพื่อ
**แยก Canva Pro 1 กับ 2 ออกจากกัน** ซึ่งเป็นปัญหาจริงเพราะสองห้องนี้หน้าตาเหมือนกัน

### แปลงไฟล์

crop กึ่งกลางเป็น 16:9 พอดี (ต้นฉบับ 1.7917 กว้างเกิน 0.8% — resize ตรง ๆ จะบีบภาพผิดสัดส่วน)
แล้วย่อเป็น 1920×1080 · **quantize 256 สี + Floyd-Steinberg dither**

| ไฟล์ | เต็มสี | 256 สี |
|---|---|---|
| `netflix1_vm.png` (ใหม่) | 1,993 KB | **745 KB** |
| `canva.png` (ทับของเดิม) | 1,930 KB | **625 KB** |
| `canva2.png` (ทับของเดิม) | 1,944 KB | **752 KB** |

เทียบภาพ crop พื้นไล่เฉด 1:1 แล้ว **ไม่เห็น banding** และขนาดพอ ๆ กับรูปห้องเดิม (683–785 KB)
สำคัญเพราะหน้าแรกโหลดรูปพร้อมกัน 6 ใบบนมือถือผ่าน LIFF

### ⚠️ ปัญหาที่เจอตอนเอาเข้าระบบ — กล่องรูปล็อกความสูงเป็น px

`.room-img` สูงคงที่ 150px และ `.room-hero` สูงคงที่ 220px คู่กับ `object-fit: cover`
→ **ยิ่งจอกว้าง ยิ่งเห็นภาพน้อยลง**

| จุด | เห็นภาพ | ตัดบน-ล่างข้างละ | ชื่อบริการที่ 12–25% |
|---|---|---|---|
| การ์ด มือถือ 375 | 78% | 11% | รอดมา 1% (เฉียดมาก) |
| การ์ด เดสก์ท็อป 528 | **48%** | 26% | **หายทั้งบรรทัด** |
| hero เต็มจอ 980 | **40%** | 30% | **หายทั้งบรรทัด** |

**แก้:** `aspect-ratio: 16/9` ทั้ง 2 จุด (ตรงกับไฟล์ 1920×1080) · hero เพิ่ม `max-width:560px`
ให้เท่าคอลัมน์เนื้อหา พร้อมแก้ `.accent-bar` ตาม ไม่งั้นแถบสียาวเกินรูปบนเดสก์ท็อป

**ยืนยันด้วยเบราว์เซอร์:** ที่ความกว้าง 375 และ 560 รูปทั้ง 4 ใบ (รวมรูปห้องเดิม) เรนเดอร์เป็น
16:9 พอดี ครอบตัด 0% — รูปห้องเดิมก็ได้แสดงเต็มภาพขึ้นด้วย

**ผลข้างเคียงที่ตั้งใจ:** การ์ดสูงขึ้น (มือถือ ภาพ 150→211px · เดสก์ท็อป 150→315px)
ถ้าไม่ชอบ revert ได้ด้วยการเปลี่ยน `aspect-ratio` กลับเป็น `height` บรรทัดเดียวต่อไฟล์

## 4.3 เพดานเวลาจองที่แสดงผล ≠ ของจริง (ผู้ใช้ทักหลัง deploy)

ผู้ใช้สังเกตว่าหน้า Netflix Pro เขียน "จองสูงสุด 3 ชม./ครั้ง" แต่จองได้ 3.5 ชม.
ตรวจแล้ว **ผิดทุกห้อง** ไม่ใช่แค่ Netflix

| ห้อง | หน้ารายละเอียดเคยบอก | จองได้จริง |
|---|---|---|
| MINI THEATER · Edutainment · Canva 1/2 · โต๊ะประชุม | 2 ชม. | 3.5 ชม. |
| Netflix Pro | 3 ชม. | 3.5 ชม. |

**สาเหตุ:** `room_detail.html` แสดง `Room.max_booking_hours` แต่เพดานจริง hardcode `210` นาที
ทั้ง [views.py](../booking/views.py) guard และ [booking.html](../booking/templates/booking/booking.html) `MAX_DURATION`
· ฟิลด์นี้ **ไม่เคยถูกส่งเข้า `room_data` ของฟอร์มจอง** จึงไม่มีผลใด ๆ
· ค่า 2 ในฐานเป็น **default ของ model** ไม่ใช่ค่าที่ใครตั้งใจกำหนด

**มติผู้ใช้:** 3.5 ชม. ทุกบริการถูกแล้ว — แก้การแสดงผลให้ตรง **ไม่เปลี่ยนพฤติกรรมการจอง**

### สิ่งที่แก้

- `service_hours.py`: เพิ่มค่ากลาง `MAX_BOOKING_MINUTES = 210` และ `MAX_BOOKING_HOURS_TEXT = '3.5'`
- `views.py`: guard ใช้ค่ากลาง + ส่งเข้า context ของทั้งหน้าจองและหน้ารายละเอียด
- `booking.html`: `MAX_DURATION` และข้อความ "สูงสุด X ชั่วโมง" อ่านจาก context (เดิม hardcode 3 จุด)
- `room_detail.html`: chip แสดงค่ากลางแทนฟิลด์
- `RoomForm` + `room_form.html`: **ถอด `max_booking_hours` ออกจากฟอร์ม** แสดงเป็นค่าคงที่ disabled
  พร้อมบอกว่าแก้ได้ที่ `service_hours.py` — กันเจ้าหน้าที่ตั้งค่าแล้วเข้าใจผิดว่ามีผล
